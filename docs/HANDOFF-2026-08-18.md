### 0.2 — 2026-08-18, audit found a latent bug that fires inside the target window

**`score.grade()` will write a false MISS into the immutable ledger on
2026-10-09.** This is the single most important thing in this document.

`grade()` matches a projection to the *nearest realized pivot of the same kind*,
with **no distance bound**:

```python
nearest = min(same, key=lambda p: abs((p["date"] - projection["date"]).days))
```

`resolvable()` returns True once `today > projected_date + tolerance_days`. For
the `2026-10-05` ATL projection that is **2026-10-09**. On that date the only
confirmed ATLs in the database are historical (newest: `2022-11-21`), so the
tracker will grade the 2026 projection against a pivot **1,414 days away** and
record `within_tolerance = 0`.

Reproduced directly:

```
resolvable on 2026-10-09? True
grade -> {'realized_date': date(2022,11,21), 'days_off': -1414,
          'within_tolerance': False}
```

**Why this is worse than an ordinary bug.** `projections` is write-once by
design and `scores` is keyed to it one-shot — a projection that has been scored
never alerts again. So this does not just print a wrong number; it **permanently
poisons the ledger** in the exact window the tool was built to watch, and it
does so silently, four days after the projected date.

**Root cause is a design gap, not a typo.** A confirmed ATL is by definition the
minimum *between two confirmed ATHs* (`pivots.cycle_lows`), so the 2026 low
cannot be confirmed until the next ATH confirms, ~2029. `resolvable()` reasons
purely about the calendar and has no concept of "the evidence needed to grade
this does not exist yet." The provisional-low machinery (`pivots.provisional_atl`,
the `scores.provisional` column) was built for exactly this and **`grade()` was
never wired to it**.

**Not fixed.** See open item 1.

**Diagnostic tell:** a `days_off` magnitude in the hundreds or thousands. Any
legitimate grade is within tens of days.

### 0.1 — 2026-08-04, the build session (reconstructed from git)

Five commits, `03b5d15` → `7cbc611`. Design spec first, then implementation,
then two bug-fix passes, then a display pass.

**Four things the implementation falsified about the design.** All four were
caught by running the code against real data, not by review:

1. **"An ATH is a high above every prior high" is wrong.** That marks every day
   of a rally as a cycle top. The rule needs a confirmation window, and
   calibrating it against 5,344 real candles showed the window is bounded on
   *both* sides — see §4 decision 2.
2. **`HISTORY_START = 2015-01-01` created a phantom ATH.** The first candle in
   the series had no prior high to be measured against, so it trivially "stood
   un-exceeded" and was promoted to a cycle top ($321 on 2015-01-01). Moving the
   start to 2012-01-01 anchors on the real 2013-11-30 peak and adds a fourth
   completed cycle. **The spec was never updated** — see §0.3.
3. **`score_claimed_legs()` zipped positionally.** Extending history backwards
   added a leg at the *front* of the list, so the post's four claimed legs were
   silently compared against the wrong realized legs. Output looked plausible —
   all four "failed" by ~700 days — which is exactly why it nearly shipped. Now
   keyed by each leg's starting pivot date.
4. **The schedule-agreement field compared the next ATL against the one four
   years later** and always read as a disagreement. Now bounded to projections
   within 180 days of the earliest upcoming one.

**Two bugs found while testing the notification (commit `763a126`):**

- **`--dry-run` was committing.** Grading is one-shot, so previewing the output
  silently consumed the real alert — the first live Discord post was missing
  both projection gradings because a dry run had already marked them scored. All
  writes now route through `commit()`, a no-op under `DRY_RUN`, plus an explicit
  `rollback()`.
- **`INSERT OR REPLACE INTO scores VALUES (?,?,?,?,?)` supplied 5 values for 6
  columns** after the `provisional` migration. It only raises when a *new*
  projection resolves, so it was masked by the two already-scored rows. Columns
  are named now. **Note this is the same class of failure as §0.2 — both are
  latent faults on the path that only executes at the October pivot.**

**One hypothesis tested and rejected — do not re-attempt without new data.** A
real-time bottom detector. Two discriminators were measured against the three
completed down legs:

- *Quiet window* ("the low has stood N days") — fails. The 2014-04-11 low stood
  **176 days** and still broke. 138d and 143d false stands also occurred.
- *Recovery magnitude* — fails, and fails backwards. The **false** low of
  2013-12-18 recovered **160%**; the **real** 2022-11-21 bottom recovered
  **18.7%** over the same horizon.

With n=3 completed cycles nothing separates. Shipped a four-tier calibrated
confidence string (`pivots.confidence`) instead of a detector.

## 1. What this is

A tracker over a specific, dated, falsifiable claim. On 2023-12-12 an anonymous
/biz/ poster (No.56956841, archived at `warosu.org/biz/thread/56956841`) asserted
Bitcoin runs a fixed cycle — 1064 days ATL→ATH, 364 days ATH→ATL — and projected
the next all-time high on **2025-10-06**. Bitcoin topped that exact day at
~$126,272. This repo pulls daily exchange candles, detects cycle pivots from raw
price data, registers future projections in a write-once ledger *before* the
dates arrive, and grades each one as it resolves — so the claim is scored rather
than argued about. **The live question is the projected cycle low on 2026-10-05
(±3 days).** Timing only; the model says nothing about price.

```
~/btc_cycle
├── btc_cycle.py    CLI + SQLite storage + orchestration      (427 lines)
├── sources.py      Bitstamp / Coinbase fetch, UTC normalize  (105)
├── pivots.py       pivot detection, confidence  [pure]       (159)
├── schedule.py     the three projection schedules  [pure]    (113)
├── score.py        grading  [pure]                           ( 59)
├── report.py       Discord embeds + text rendering           (208)
├── test_btc_cycle.py                          20 tests       (196)
├── ops/run_btc_cycle.sh              keychain wrapper
├── ops/com.btccycle.snapshot.plist   launchd, daily 09:10
├── btc_cycle.db    SQLite  [gitignored]
└── logs/           launchd out/err  [gitignored]
```

`pivots.py`, `schedule.py` and `score.py` are pure functions over plain data —
no network, no database, no clock. That is deliberate: the pattern logic is the
part that must be correct, and it is testable without touching an API.

## 2. Data flow as it actually is

```
Bitstamp OHLC ──backfill 2012→now──┐
(1000/req, paginated)              ├──► candles ──► pivots.detect() ──► pivots
Coinbase candles ──daily tick──────┘   (SQLite)     CONFIRM_DAYS=270
(290d pages, primary; Bitstamp fallback)                 │
                                                         ▼
                                        schedule.all_projections()
                                        oracle / derived / ath_to_ath
                                                         │
                                                    projections  (WRITE-ONCE)
                                                         │
                                              score.grade() when window closes
                                                         │
                                                       scores
                                                         │
                                    report.py ──► 2 Discord embeds ──► webhook
```

Daily run refetches a **7-day trailing window**, so a missed run self-heals the
price series. Verified in production: the 2026-08-15 candle was written on
2026-08-16 after a DNS failure. The `snapshots` row for that day is gone for
good — snapshots are per-run only and are never backfilled.

### SQLite schema (`btc_cycle.db`, created by `SCHEMA` in `btc_cycle.py`)

| table | rows (2026-08-18) | notes |
|---|---|---|
| `candles` | 5,344 | 2012-01-01 → 2026-08-18. 5,330 bitstamp, 14 coinbase |
| `pivots` | 7 | PK `(date, kind)` |
| `projections` | 11 | **write-once.** `UNIQUE(schedule, kind, projected_date)` |
| `scores` | 2 | PK = `projection_id`. One-shot: scored ⇒ never alerts again |
| `snapshots` | 14 | one per successful run since 2026-08-04 |

**No retention policy anywhere.** No pruning, no VACUUM, no expiry. At ~365
candles + 1 snapshot per year this is fine indefinitely; do not "fix" it.

## 4. Decisions made, with the rejected alternative

**1. Two exchange APIs, no key.** *Rejected: CoinGecko*, which was the first
choice and is in the original design conversation. Its free tier is **capped at
365 days of history** (`error_code: 10012`), which kills the backfill outright —
and the backfill is the test. Bitstamp reaches 2011 and Coinbase matches the
exchange the $126k headlines quote, so both are used: Coinbase primary for the
daily tick, Bitstamp for depth and as fallback.

**2. `CONFIRM_DAYS = 270`, calibrated, not chosen.** *Rejected: any round
number.* Measured how long each running-max high stood un-exceeded across the
real series:

| high | stood | cycle ATH? |
|---|---|---|
| 2017-12-17 | 1079d | yes |
| 2021-11-10 | 846d | yes |
| 2025-10-06 | 302d and counting | yes |
| **2024-03-13** | **237d** | **no — nearest false positive** |
| 2021-04-14 | 189d | no |

Only **238–302** works, and both edges bind: under 238 the March 2024
consolidation peak is promoted to a cycle top; over 302 the 2025 ATH cannot be
confirmed yet. `CONFIRM_MIN/CONFIRM_MAX` and two tests pin both edges. **If you
change this constant, run the tests — they exist to stop exactly that.**

**3. Three schedules, tracked in parallel.** *Rejected: picking one.* `oracle`
is the post's literal chain from its own 2021-11-08 anchor; `derived` applies
the same 152w/52w rule to realized pivots; `ath_to_ath` uses the tighter
empirical 1425d ATH→ATH spacing. They matter because the post's headline call
**does not reproduce from real data** — chaining from the actual 2022-11-21 low
gives 2025-10-20, two weeks late. The 2025-10-06 figure came from chaining
through a projected 2022-11-07 low that never happened. The ledger records both:
`oracle ATL 2022-11-07 → +14d MISS`, `oracle ATH 2025-10-06 → +0d HIT`.

**4. Write-once projections, grades in a separate table.** *Rejected: one table
with a mutable status column.* A projection that can be updated is a projection
that can be quietly moved after the fact — which is precisely how the source
material got away with its chaining. The separation is the integrity guarantee.

**5. Report calibrated confidence, not a bottom call.** *Rejected: a
provisional-ATL detector* — see §0.1 for the two discriminators tested and why
both fail. Also *rejected: a wider tolerance band.* ±3 days scores the post's
own history at 2/4; a band fitted to make the source look good would defeat the
purpose. `days_off` is always stored exactly, so any band can be re-applied to
stored scores without a re-run.

**6. Rival timing hypotheses — considered and DECLINED 2026-08-18.** Adding
halving-anchored and election-anchored schedules to turn the ledger into a
cross-theory scoreboard. The machinery supports it; the user wants the tracker
focused on the /biz/ claim alone. **Do not re-pitch.** Numbers if it ever comes
back: halving mean-lag 2026-08-31, biz 2026-10-05, halving last-two-lag
2026-10-13, election trend 2026-10-18, election mean-offset 2026-12-14 (105-day
spread). The election reading contradicts *itself* by 57 days off the same three
points — the cleanest illustration in this project of why n=3 cannot support
curve-fitting.

**7. launchd at 09:10, no jitter.** *Rejected: matching the Kalshi job's 09:00.*
Ten minutes of offset keeps the two Discord posts out of the same second and
keeps the logs readable when both fail on one network blip. No jitter because
this hits documented public exchange APIs where a predictable daily timestamp
makes the price series cleaner — unlike the dispensary digest, which randomizes
to avoid looking like a fixed-schedule scraper.

## 5. Gotchas — every one of these cost real time

### Time zones

**Exchange candles are stamped at UTC midnight. Converting with a local-time
call shifts every candle back one day in US Eastern.** This produced
2017-12-**16** / 2021-11-**09** / 2025-10-**05** — each exactly one day early —
and it is *invisible on a price chart*. The whole tool is day counts, so a
one-day systematic slip is fatal and undetectable by eye.

All conversion goes through `sources._utc_date()`. **Never call
`date.fromtimestamp` or bare `datetime.utcfromtimestamp` in this repo.**
`TestUTC` pins three known epochs.

*Diagnostic tell:* every pivot is exactly one day earlier than the canonical
date. If one pivot is off, it is data. If *all* are off by the same amount, it
is the clock.

### Latent faults on the October path

Two bugs (§0.1 item 5, and §0.2) were both invisible because **the code path
that grades a newly-resolved projection has never run in production.** The only
two scored rows were written by a backfill of already-resolved history. Anything
touching `resolve_projections` / `grade` / the alert embeds is effectively
untested against reality. **Assume that path is broken until you have exercised
it deliberately** — see the commands in §8 for how to rehearse it without
touching the real DB.

### Positional SQL after a migration

`INSERT ... VALUES (?,?,?,?,?)` broke silently when `provisional` was added.
**Name your columns in this repo.** The table has a migration in `connect()` and
will likely get another.

### `--dry-run` used to mutate

Fixed, but understand why it mattered: grading is one-shot, so a preview that
commits *consumes the real alert*. If you add a new write path, route it through
`commit()` — the module-level `DRY_RUN` no-op — not `conn.commit()`.

*Diagnostic tell:* an alert you expected never arrives, and the corresponding
`scores` row already exists with a `scored_at` timestamp from when you ran the
preview.

### Network failure is silent

`fetch_daily` tries Coinbase then Bitstamp and raises `SystemExit` if both fail.
launchd captures that to `logs/launchd.err` and **nobody is notified.** The
2026-08-15 run died this way and was only discovered by reading logs 3 days
later. The 7-day trailing refetch means the *candle* self-heals; the *snapshot*
does not.

### Python 3.9

Host runs 3.9.6. **No `X | None` unions**, no `match`. Same constraint as
dispensary_index.

## 6. Open items, priority order

### 1. Fix `score.grade()` before 2026-10-09 — **HARD DEADLINE**

See §0.2. On 2026-10-09 the tracker permanently writes a false MISS against the
2026-10-05 projection, matched to a pivot from 2022. This is the tool's whole
purpose and it will get it wrong, silently, in the write-once ledger.

Sketch of the fix — three parts, all needed:

1. **Bound the match.** `grade()` must refuse a candidate pivot further than
   some sane window (a leg length, 364d, is the natural bound) and return
   `None` rather than a wild `days_off`.
2. **Distinguish "unresolved" from "missed."** `resolvable()` currently reasons
   only about the calendar. A projection whose *evidence* cannot exist yet — an
   ATL with no subsequent confirmed ATH — is not resolvable at any date.
3. **Wire the provisional path.** `provisional_atl()` and `scores.provisional`
   were built for this and are dead code. A provisional grade should be
   recorded with `provisional=1` and **re-graded** when the definitive pivot
   confirms, which means `scores` can no longer be strictly one-shot for
   provisional rows.

Part 3 is a real design change, not a patch. Do not skip parts 1 and 2 waiting
to get part 3 right — parts 1 and 2 alone stop the ledger being poisoned.

### 2. Rehearse the October alert path

Every alert that matters in the window has only been rendered by hand. Before
2026-10-02, drive the whole path against a copy of the DB with a synthetic
in-band low and confirm: the `IN BAND` embed fires, the grade is right, and the
`scores` row is what you expect. See §8.

### 3. Add failure alerting

A silent dead job is the failure mode that makes the whole thing worthless — it
will look exactly like a quiet market. dispensary_index has a watchdog pattern
worth copying. Minimum viable: if the last `snapshots` row is more than 2 days
old, post to Discord.

### 4. Update or supersede the design spec

Four stale claims, listed in §0.3. Either amend the spec in place or mark it
historical and let this handoff be the reference for current behaviour.

### 5. `derived` has never diverged from `oracle`

They have agreed on every date so far, so `derived` has never been
independently tested. It will diverge if the 2026 low lands off 2026-10-05.
Nothing to do now — just do not read its agreement as corroboration.
